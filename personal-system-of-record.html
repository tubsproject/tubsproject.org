🛁 The Ultimate Bookkeeping System (TUBS)

Personal system of record

Design notes, November 2026. This is a design in progress. The status table says what exists, what is proposed and what is undecided.

What it is

A personal system of record is the place where a person's own data is authoritative for them: bookkeeping, issues, messages, notes, photos and documents, together with the history of how each item changed and why.

It differs from a personal data store or pod in what the term names. A store or pod is a place that holds data for applications. A system of record is a role: it is where the authoritative version, its history and its provenance are kept. A pod or personal data server can be one of the storage backends that a personal system of record indexes.

Authority here is personal, not global. A bank's ledger is authoritative for the bank, and your record of the same transaction is authoritative for you. This is the multi-homed data that TUBS describes. Messaging and schema translation reconcile the copies.

Principles

  1. Original bytes are permanent; interpretation is rebuildable. Files and raw API responses are kept exactly as received. Records, schemas mapped onto them, and indexes are derived and can be regenerated.
  2. Identity is content, never location. Content is named by a hash of its bytes. Where it is stored is recorded separately and can change without changing any identity.
  3. Indexes and views are disposable. Any folder layout, database or application view can be deleted and rebuilt from the content and the log.
  4. An annotated history of data and schemas. Both the data and the schemas evolve, and both evolutions are kept. Every change to either is an entry in one log, annotated with a free-form message saying what happened and why. There is one layer of annotations, not one per tool.
  5. Files stay where they are. Existing folders on existing storage are indexed in place. Nothing has to be moved or renamed before the system is useful.
  6. Existing sync engines are used, not replaced. Storage providers already move bytes between devices and the cloud. The system of record adds an index and a history on top of them.
  7. Signatures, identity and sharing sit above the core. The core needs hashes, a log and an opaque author label. A counterparty's signature is stored as part of the message it arrived in.
  8. No marriage to one tool. The durable formats are simple enough to re-implement a reader from the bytes alone.

Definitions are not disposable. A translation between two schemas encodes judgement, and regenerating it may not give the same result. Output that has left the system, such as a sent message or a filed return, is also kept as content, since it is a fact about what was said.

Storage providers and their sync engines

Most people's files already sit with one or more storage providers, and each provider ships a sync engine: a desktop client that mirrors a folder, or a phone feature that uploads new photos. A personal system of record builds on these. It does not need its own way of moving bytes between a phone, a laptop and the cloud.

What a provider and its sync engine contribute

  • Capture. Automatic photo upload gets new data off a phone without any action by its owner. This is the hardest part to replace, and there is no need to.
  • Storage. The provider holds the bytes and can count as one of the required copies.
  • Replication. A synced folder carries files between devices. It can also carry the system of record's own content and log files to other machines.
  • A temporary safety net. Where a provider keeps earlier versions of a file for a period, a replaced or deleted version can still be fetched during that period.

What they do not provide

  • History beyond the provider's retention period, or any record of why something changed.
  • A view across providers: which files are the same, and which exist in only one place.
  • Verification under your own control, independent of the provider's account and client.
  • Immutability. Any connected device or application can change or delete a synced file.

The index and the log supply these.

How each kind of storage is indexed

The index reads metadata only. File bytes are not downloaded unless a policy asks for a local copy. The details below need checking against each provider's current documentation before they are relied on.

Google Drive HTTP API file listing Yes: checksums reported per file Changes feed

iCloud is the case without a web API. Apple does not offer third parties a service API for listing a user's iCloud Drive or photo library. On a Mac, however, the provider's own sync engine exposes both through local interfaces: iCloud Drive as files in the file system, and the photo library through the system's photo framework. An indexer running on that Mac reads those, so the Mac's sync engine acts as the adapter. The same local scan covers ordinary folders.

Providers report different hashes for the same bytes. The index therefore keeps a set of hashes for each piece of content, and links two hashes only after the same bytes have been hashed with both. Until then, the same size and name on two providers is recorded as a probable match, not as identity.

Locations, copies and verification

  • Locations are observations. "This backend reported this content at this path and revision, at this time" is recorded with the date and the method of verification. A later scan that finds something else is a new observation.
  • Backends have properties: whether a copy there counts, whether the backend is immutable, versioned or mutable, how content is verified, and how quickly it can be retrieved.
  • A required number of copies. The system reports content with too few copies on backends that count, and whether removing a copy is safe. A phone's cloud upload is the second copy of a new photo until another backend has it.
  • Detection and rescue. Mutable storage cannot be made immutable from outside. Changes are detected by scanning, recorded in the log, and the superseded version is fetched from the provider's version history before it expires.
  • The index is backed up to more than one backend. If it is lost, files indexed in place are still usable under their original paths.

Using a synced folder as transport

A provider's synced folder can replicate the system of record's own files, which removes the need for a separate copy step. Sync engines are built for ordinary documents, so a few rules apply:

  • Put only immutable files in the synced folder. Content named by its hash and finished log entries qualify.
  • Write a file somewhere else on the same disk first, then move it in, so the sync engine never sees a partial file.
  • Keep lock files, temporary files and databases out of the synced folder.
  • Let one machine write any file that is updated in place, such as the pointer to the newest log entry. Two writers produce conflicted copies.
  • Bundle many small files into one archive file per day. Sync services and cold storage both slow down or charge by the number of files.
  • Expect files that are stored online only. Verifying them by hash means downloading them.

Setting one up with SyncD

SyncD, the standalone Syncables daemon, is the indexer. It runs on your laptop, imports data from many platforms through an integration-proxy instance such as IAP, and keeps the data, its schemas and their history with commit messages in a local database. It already keeps inventories of the files you hold with Dropbox, Google Drive and iCloud Drive, and it works alongside the providers' own sync clients.

The SyncD page describes what it does today and what is planned. The daemon guide has the exact commands.

A plain-file form of the record

A database is a working store, not the permanent record. The record also needs a form that can be read without the software that wrote it. The proposed form is a directory of plain files:

  • Content in files named by the SHA-256 of their bytes, in subfolders named after the first two hexadecimal characters.
  • Log entries as small JSON files, themselves named by their hash. Each holds the hash of the previous entry, the hashes of the content it concerns with provenance notes such as the original path, and the commit message.
  • One pointer to the newest entry, the only file that is ever replaced.

Everything in it can be checked with standard tools: hash each file and compare with its name, then follow the chain of entries. New files can be bundled into one archive file per day for transport to a sync folder or cold storage.

The plan is for SyncD to write this form as an export of its own history, alongside its existing Git export, carrying the same commit messages. The log stays SyncD's, so there is one layer of messages, and the directory is a durable view of it. A small command-line prototype of the format exists; it is not developed as a separate tool.

Structured data

For API data, SyncD keeps the original response text, a content-addressed graph of the JSON, and snapshot revisions with commit messages. Schemas are versioned in the same revisions as the data, as described in Versioned Atomic Data.

Fine-grained hashes serve different purposes at each level: a value hash identifies content wherever it appears, an atom hash identifies a statement about a subject, and a record hash identifies the full state of one resource. All of them can be computed from the same stored bytes, so the choice of what to hash is separate from the choice of what to store as a unit.

Writes

A write through a view is recorded first and interpreted afterwards. The raw event, for example "the file at this path now has this hash", is kept as a fact, and its meaning is derived and can be revised.

Free-form intent is preferred over fixed buttons. The user's own words become the commit message, and the concrete operations that resulted are recorded with it, because an interpretation by a language model is not reproducible. Actions that leave the system and cannot be undone by appending, such as sending a message or making a payment, show a preview first.

Integrity

  • Each log entry includes the hash of the previous one, so any change to history is detectable.
  • A copy of the log head held outside the system detects a rollback. A write-once offsite copy serves this purpose, and so does a timestamping service. A provider that keeps version history for the head pointer is an informal witness.
  • Signing checkpoints with a key kept elsewhere is optional and is layered on top.

Messaging and translation

Planned as the next stage.

  • A received message is stored byte-exact, with its envelope, as content.
  • The result of verifying a signature is recorded as an observation at the time of receipt, since keys expire and rotate.
  • Translations between schemas are stored, versioned definitions. The original is always kept, because translation loses information in both directions.
  • Only the author supersedes a record. Others send a message proposing a change.

Decision log

2026-11-10: Content and log as the core
Whole files named by SHA-256, plus a hash-chained log of small entries with free-form messages. Files are not split into chunks, so the store stays readable with ordinary tools.
2026-11-10: Signatures out of the core
Hashes give integrity for a single writer. Signatures answer "who said this", which belongs to messaging and sharing. Building one identity scheme into the core would make it harder to evolve.
2026-11-10: Not built on Perkeep
Its blob and index layers match this design, but it requires signed claims, has a fixed schema vocabulary and chunks large files.
2026-11-10: Custom pack files considered, then dropped
Packing many small JSON nodes into immutable files needs an index, location hints and consolidation. Git already solves all of these.
2026-11-10: Git bundles considered, then dropped
Storing Git history inside the log would create two layers of commit messages describing the same events.
2026-11-10: Aggregation is a transport concern
Per-file costs come from sync services and cold storage, not from the local file system. Locally, loose hash-named files are enough. For transport, new files are bundled into a standard archive file.
2026-11-10: Raw responses are the permanent unit for API data
A full export across many services could reach tens of millions of JSON nodes, too many for one file each. Response pages number in the tens of thousands. Nodes stay in a database as a working index.
2026-11-10: Databases are working stores
PostgreSQL, an embedded key-value store, or a document database can each hold the index. None is the permanent record, and the choice can change without changing any hash.
2026-11-11: SyncD stays on PostgreSQL for now
The reason to change its storage is a single store that also covers files and photos. Until that exists there is no benefit.
2026-11-11: Existing folders are indexed in place
Reorganising large existing collections is unnecessary. Immutability is replaced by detection and rescue.
2026-11-11: One index over several backends
Storage providers are treated as backends with stated properties. SyncD is the indexer.
2026-11-13: A home server is optional
Below the common cloud storage tiers, a home server does not save money, and the design does not depend on one. An independent second copy matters more than where the first copy lives.
2026-11-16: Sync engines are used, not replaced
Providers' own clients keep handling capture and replication. For iCloud, which has no web API for listing, the index reads the local interfaces on a Mac.
2026-11-17: One log, owned by SyncD
A separate content-and-log tool beside SyncD would mean two logs with two layers of commit messages. Its plain-file format is kept as a planned export from SyncD instead.
2026-11-16: The name
"Personal system of record", shortened to "personal SoR" in running text.
