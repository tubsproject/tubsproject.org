🛁 The Ultimate Bookkeeping System (TUBS)

SyncD

SyncD is the standalone Syncables daemon. It runs on your own laptop, imports your data from the platforms you use, and keeps a local, annotated, versioned archive of it: the records, the schemas that describe them, and the evolution of both, with every change annotated to say what changed and why. It is the indexer for a personal system of record.

SyncD is experimental. It is the trailblazer project for the Syncables stack and for IAP: new features of both are exercised here first, so details on this page will change. The daemon guide in the repository has the exact commands and current limits.

Where it runs

On the user's laptop, as a process started from the syncables command. The archive, the collection settings and the history stay on that device. There is no hosted SyncD service that holds your data. A laptop sleeps; SyncD catches up when it wakes.

Importing from platforms

Your issue tracker, notes, tasks, calendar, bookkeeping package and chat each hold part of your record behind an API. SyncD does not need a hand-written integration for each of them. It is a generic API client: it reads a machine-readable description of a platform's API and works out from that how to fetch every record in a collection.

How a platform becomes importable

  1. An API description. Most come from the OpenAPI directory or from the provider itself.
  2. A description of its behavior. OpenAPI extensions add what an API description usually leaves out: which operations list a collection, how to reach the next page, what identifies a record, how deletions show up, and what rate limits apply.
  3. An overlay attaches that behavior to the provider's description without editing it. The overlays cover more than a hundred APIs.
  4. A dated catalog pairs each description with the overlay revision to use, so a sync can say exactly which description it followed.

The most recent catalog lists Airtable, Asana, Box, Clockify, Discord, Dropbox, GitHub issues, GitLab, Google Calendar, Google Drive, Google Keep, Google Tasks, Moneybird, Notion, Spotify and Todoist. How far each has been tested against the live service varies; GitHub issues and Google Keep are the reference examples in the daemon guide. Adding a platform is mostly a matter of writing an overlay, not code.

Connecting through IAP

SyncD reaches platforms through an instance of integration-proxy. Integrations Atomic Place (IAP), at integrations.atomic.place, is one such instance. Any other deployment works the same way, including one you host yourself.

  • The proxy holds the provider credentials and grants. You approve a device session for SyncD, and choose which connections it may use. SyncD never receives the provider's tokens.
  • SyncD holds the data. The proxy forwards requests; imported records and their history are stored only on the laptop.
  • Change hints while the laptop sleeps. The proxy can receive a platform's webhooks and keep only the fact that something changed, discarding the content. SyncD collects these hints later and reads the changes itself.
  • Grants stay under your control. A local control panel lists connections, app delegations and sessions, and can revoke any of them.

What a sync does

  • Reads the whole collection, following the declared pagination page by page, not just the first page.
  • Reads only what changed on later syncs, where the API offers a change feed or other incremental read.
  • Publishes all or nothing. A new revision appears only after the complete read succeeds. If a read fails halfway, the previous revision stays current.
  • Keeps the evidence. Every response is stored as the exact text the platform returned, so a record can always be traced to what the API actually said.

What it stores

By default, everything goes into a local PostgreSQL database:

  • The records, as Atomic Data resources with stable identifiers, and the original JSON kept alongside. Fields SyncD does not understand are retained, and numbers keep their exact spelling.
  • The schemas, as class and property resources versioned together with the data that uses them. Reading an old revision interprets it with the schema as it was then.
  • The history, as revisions. Earlier states remain readable, including records that disappeared and came back.
  • Annotations, on every revision, covering changes to data and schemas alike, as commit messages. SyncD writes what was synced and how; you can add why: 
    syncables sync --config config.json \
  --message "Snapshot before migrating to the new tracker"

Using the data

The archive can be browsed offline, from the command line or a local browser interface, at the current revision or any earlier one.

Exports

The archive in PostgreSQL is the richest form of the data: records, their schemas, and the annotated evolution of both. Every other form is an export of it, and carries as much as the target can hold.

  • Git exports the history of a collection or a single record, with its messages and branches.
  • Braid serves a collection over Braid-HTTP. A client subscribes and receives each new revision as it is published.
  • Plain folders hold one JSON file per record, with the schemas alongside.
  • The Atomic drive presents the synced collections as one drive, with a table per collection, which Atomic clients and servers can replicate. Each record notes the archive revision it came from.

Atomic Data is the model SyncD works in, so an Atomic drive is the export closest to the archive, and Atomic Server is where we would like the archive itself to live. What it lacks is the annotated evolution of data and schemas: their versions, and the annotations explaining them. Versioned Atomic Data is the proposal to add them.

Possible further targets include a plain-file form of the archive (see the design page), personal data store protocols such as remoteStorage, Solid and LWS, Perkeep and Nextcloud. What each of them can keep is still to be assessed.

Sending changes back

Experimentally, SyncD can queue local creates, edits and deletes and send them to the platform through an owner-approved session on the proxy. It does so only for operations that the API description declares precisely enough, and refuses the rest. Google Keep is the first composed example. This has been tested against invented providers; live writes are not yet verified. Editing a checked-out file never sends a write by itself.

Files at storage providers

SyncD can also keep an inventory of the files you hold with Dropbox, Google Drive and iCloud Drive. It records metadata only: names, paths, sizes, revisions and the checksums a provider reports. Dropbox and Google Drive are read through their APIs. iCloud Drive, which has no listing API for third parties, is read from the folder that the Mac's built-in sync client maintains, without opening or downloading files. A duplicate report separates confirmed matches, with equal checksums, from candidates that only share a name and size. See the file inventory guide.

SyncD works alongside the providers' own sync clients rather than replacing them: the client moves the bytes, SyncD records what exists and how it changes. Joining a provider's API view with its local synced folder, to confirm copies by checksum, is proposed in atomic-plugins #727. The design page describes the role of storage providers in more detail.

Planned: storing copies

SyncD currently keeps its archive on the laptop. A later stage is to store copies in places you choose, such as an atomic.place account, an ELFA/NextGraph account or your Dropbox, with a stated number of copies required before any source is considered safe to remove.
