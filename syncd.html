🛁 The Ultimate Bookkeeping System (TUBS)

SyncD

SyncD is the standalone Syncables daemon. It runs on your own laptop, imports data from the platforms you use, and keeps a local, versioned archive of it. It is the indexer for a personal system of record.

SyncD is experimental. It is the trailblazer project for the Syncables stack and for IAP: new features of both are exercised here first, so details on this page will change. The daemon guide in the repository has the exact commands and current limits.

Where it runs

On the user's laptop, as a foreground process started from the syncables command. The archive, the collection settings and the history stay on that device. There is no hosted SyncD service that holds your data.

A laptop sleeps. SyncD catches up when it wakes, using each provider's change feed where one exists.

Connecting to platforms

SyncD reaches most platforms through an instance of integration-proxy. Integrations Atomic Place (IAP), at integrations.atomic.place, is one such instance. Any other deployment of integration-proxy works the same way, including one you host yourself.

  • The proxy holds the provider credentials and grants. SyncD receives a device session approved by the owner, not the provider's tokens.
  • SyncD holds the data. Imported records and their history are stored on the laptop, not in the proxy.
  • Change hints while the laptop is asleep. The proxy can receive a platform's webhooks and keep only a notification that something changed, without storing the content. SyncD collects the hints later and reads the changes itself.
  • Grants can be reviewed and revoked from a local control panel that SyncD serves on the laptop.

Which platforms can be imported depends on the API descriptions and overlays available for them. See From APIs to Atomic Data.

What it stores

By default, everything goes into a local PostgreSQL database:

  • The synced data, as Atomic Data resources, with the original API response text retained alongside.
  • The schemas, as class and property resources versioned together with the data that uses them.
  • The history, as revisions. Each successful sync publishes one, and earlier revisions remain readable.
  • Commit messages, on every revision, covering changes to data and to schemas alike. A generated line says what was synced and how, and your own stated intent is recorded with it.

The stored data can be browsed offline at any revision, from the command line or a local browser interface. A collection can be checked out as a folder of JSON files, and its history can be exported to Git.

Files at storage providers

SyncD can keep an inventory of the files you hold with storage providers. It imports metadata only: names, paths or identifiers, sizes, modification times, revisions and the checksums a provider reports. It does not download or open file contents.

SourceHow it is readLater syncs
Dropbox The provider's API, with a read-only metadata grant A cursor reports additions, changes and deletions
Google Drive The provider's API, with a read-only metadata grant The change feed
iCloud Drive The iCloud Drive folder on a Mac: directory entries and file attributes, including files that are stored online only The folder is scanned again

A duplicate report runs over the stored inventories. It separates confirmed duplicates, where two files have the same checksum of the same kind, from candidates, where files on different providers share a name and size but their content has not been compared. The file inventory guide covers setup.

Alongside the platform's own sync client

Most laptops already run sync clients. macOS has iCloud built in, and most Dropbox users have a Dropbox folder. SyncD is meant to work next to these, not to replace them. The sync client moves the bytes. SyncD records what exists, where, and how it changed.

What works today

  • iCloud Drive through the Mac. Apple offers no listing API to third parties, so SyncD reads the folder that the built-in sync client maintains. That client is the adapter.
  • No downloads triggered by a scan. Files stored online only appear as placeholders. SyncD lists them and reads their attributes without opening them. For that reason the iCloud inventory has no checksums.
  • Dropbox and Google Drive through their APIs. This gives the complete listing, including files that are not on the laptop, with the provider's own checksums.

What is proposed

Where a provider has both an API and a local synced folder, the two views can be joined. This is design, tracked in atomic-plugins #727.

  • Confirming the sync client's work. A provider's checksum can be recomputed from a file that is present locally. If it equals what the API reports, the file is verified to exist in both places.
  • Linking checksums. A file that is present locally can also be hashed with a universal algorithm, which ties the provider's checksum to one that other providers can be compared with.
  • Writing through the synced folder. To place a copy with a provider, SyncD can put a finished file into the synced folder and let the client upload it, then confirm arrival through the API.
  • Separate grants for reading and writing. Reading metadata across an account and writing into one dedicated folder are different authorities and should be approved separately.
  • Backing up the archive. A regular export of the database written into two providers' synced folders gives two offsite copies.

Local presence is not proof of a remote copy, since a file may be unsynced or in conflict. SyncD and a sync client must also never both write the same file, and the database itself stays out of synced folders.

Planned: storing copies

SyncD currently reads. A later stage is to let it store copies of your data in places you choose, for example an atomic.place account, an ELFA/NextGraph account, or your Dropbox. Each destination would be recorded as a location, with a stated number of copies required before any source is considered safe to remove.
